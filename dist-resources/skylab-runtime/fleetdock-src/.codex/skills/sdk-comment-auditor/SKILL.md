# SDK 注释审校

## 工作流

1. 读取仓库根目录的 `AGENTS.md`、公共导出文件和本次改动，确认项目术语与注释规范。
2. 优先审查用户指定文件；未指定时，先检查 Git 改动，再检查公共 SDK 入口及其直接关联实现。
3. 运行静态扫描脚本生成候选问题：

```powershell
python .codex/skills/sdk-comment-auditor/scripts/audit_sdk_comments.py fleetdock
```

若项目指定了 Python 路径，使用项目指定解释器。脚本结果只是线索，不得替代语义审查。

4. 结合源码判断符号是否面向 SDK 使用者。重点追踪：
   - `__all__` 和包级导出；
   - 公共设备对象、任务编排对象、配置和响应数据对象；
   - 枚举类及每个枚举成员；
   - 工厂、注册表、适配器公共入口；
   - 事件类型、事件数据、订阅和取消订阅入口；
   - 示例中直接暴露给开发者调用的方法。
5. 直接补充或重写不合格注释，保持行为、签名和类型不变。
6. 复查改动并运行相关测试。若修改了模块，按仓库规范同步中文 `README.md`；若只修改 docstring，也要确认 README 中没有与新说明冲突的内容。

## 审校标准

公共类和方法使用中文 docstring，使 IDE 无需跳转实现即可理解。

公共方法说明至少覆盖适用项：

- 方法用途和可观察行为；
- 关键参数的业务语义，而非重复参数名；
- 数值单位、坐标系、范围、可空语义和默认行为；
- 命令何时发送、状态何时生效、回调何时执行；
- 返回值含义，包括成功、失败或取消订阅函数；
- 重要异常、安全边界、资源释放责任和前置条件。

公共类、数据对象和事件模型说明至少覆盖适用项：

- 对象在公共 SDK 中的职责；
- 字段的业务语义、单位、坐标系和缺失值含义；
- 生命周期、可变性或线程/异步使用限制；
- 标准模型与厂商原生数据的关系。

枚举类说明枚举整体用途；每个成员使用中文行内注释或紧邻注释说明业务语义。涉及状态、错误码、单位、坐标系或适用场景时必须明确，不能只把英文标识符翻译成中文。

## 修改原则

- 优先写“调用者需要知道什么”，不要复述实现步骤。
- 不为简单私有辅助函数机械补注释；仅在复杂逻辑、安全边界或非显然约束处补充。
- 不用“处理数据”“执行命令”“获取结果”等空泛句子。
- 不虚构协议保证、单位、坐标系、异常或返回行为；无法从代码和测试确认时，继续追踪调用链。
- 保持术语一致：代码标识符、产品键、协议名和命令名保留英文，用户说明使用中文。
- 修改关键路径时检查模块级 `DEBUG` 日志是否满足仓库规范，但不要把日志工作扩大为无关重构。

## 验证

再次运行扫描脚本，确认目标文件不再有明显缺失项：

```powershell
python .codex/skills/sdk-comment-auditor/scripts/audit_sdk_comments.py fleetdock --strict
```

随后运行与改动范围匹配的测试。FleetDock 默认使用：

```powershell
C:\ProgramData\anaconda3\envs\fleetdock\python.exe -m unittest discover -s tests
```

若指定解释器不存在，报告实际使用的替代解释器；不要假装测试已运行。

最终说明应列出审查范围、主要注释改进和验证结果。若仍有无法确认的语义，明确指出对应文件和符号。
