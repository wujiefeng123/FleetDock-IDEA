# FleetDock 质量审计

## 原则

- 默认只读审计并报告，不修改代码；只有用户明确要求修复时才实施改动。
- 以“开发者无需理解厂商差异即可完成任务”为最高验收目标。
- 区分接口存在、Mock/注入测试通过、SITL 通过、受控真机通过和生产可用，禁止互相替代。
- 将重复出现在 Demo 中的循环、转换、重试、确认、同步和安全逻辑视为 SDK 抽象候选。
- 先报告会误导使用者或造成错误控制的事实问题，再报告风格和完整性问题。

## 执行流程

1. 完整读取仓库 `AGENTS.md`、公共导出、产品注册表、设备对象、适配器基类、PX4 适配器、任务编排入口、示例导航和支持矩阵。
2. 完整读取 [quality-gates.md](references/quality-gates.md)，按其中门禁和评分标准审计。
3. 使用项目指定 Python 运行静态扫描：

```powershell
C:\ProgramData\anaconda3\envs\fleetdock\python.exe .codex\skills\fleetdock-quality-auditor\scripts\audit_fleetdock_quality.py .
```

4. 追踪至少五条真实调用链：连接、起飞/返航、移动/航线、传感器/事件、Fleet 混合设备计划。逐条确认 `Demo → 公共 SDK → 标准命令/任务 → 适配器 → 厂商 SDK/协议`，标记直接调用厂商 SDK、CLI 或假客户端的例外。
5. 对每个内置产品核对 `maturity`、`supported_commands`、`capabilities`、`supported_events`、适配器注册和处理器实际行为。处理器存在但固定返回 `UNSUPPORTED_COMMAND` 也算契约不一致。
6. 分别检查 `examples/quickstart/`、单问题 Recipe 和高级 Scenario；不要用高级场景的复杂度否定 Quick Start，也不要把高级场景宣传成新手模板。
7. 运行仓库规定的单元测试、覆盖率、Ruff、mypy 和构建命令。记录实际结果、跳过项和环境阻塞，不把 Mock 或注入测试描述成真实 PX4 验证。
8. 检查 Git 状态，确认审计没有修改用户文件。若工具生成受忽略缓存，只报告，不删除用户既有文件。

## 语义审查重点

- 公共 API 是否用业务意图命名，参数是否统一说明单位、范围、坐标系和完成时机。
- `timeout_s`、取消、重试、守卫、返航兜底等参数是否真的进入执行链，而不只是保存到模型。
- 即时响应是否只表示命令被接受；物理完成是否由任务状态和遥测确认。
- 跨品牌应用是否需要判断 vendor、导入原生对象、解析原始 topic 或转换 NED/ENU/FRD。
- 混合 Fleet 是否能按设备类别/能力选取目标，汇总成员结果，并定义部分失败策略。
- 生命周期、后台线程、事件订阅、传感器后端和托管对象所有权是否清楚且可释放。
- 安全限制、遥测过期、低电量、设备间距、禁区、急停和失败补偿是否由 SDK 承担。
- 日志和错误是否能定位设备、命令和任务，同时避免敏感参数泄漏。
- 稳定 API、版本、支持矩阵、README、测试和真实实现是否一致。

## 报告格式

用中文输出，先给结论，再给证据。报告必须包含：

1. 一句话成熟度结论，以及“适合新手/SITL/受控真机/生产”的边界。
2. 九个质量维度的 0 ～ 5 分评分和主要扣分原因。
3. 按 P0、P1、P2 排序的问题；每项给出可点击文件与行号、实际影响和建议方向。
4. 明确回答：Demo 是否简单、功能是否形成常见任务闭环、是否全部通过 SDK/协议、封装是否产品化。
5. 分开列出 PX4、机器狗、其他品牌的真实成熟度。
6. 验证记录：测试数、跳过项、覆盖率、静态检查、构建结果和未执行的真机验证。
7. 最多三阶段的整改顺序：先修真实性与安全，再收敛 Demo，最后扩展品牌和运维能力。

没有发现问题时也要列明审查范围和尚未被证据覆盖的风险，不能用“测试通过”推导“真机生产可用”。
